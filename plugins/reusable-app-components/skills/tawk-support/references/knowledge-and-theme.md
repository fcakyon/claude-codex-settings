# Knowledge and theme

Use an existing property when it belongs to the product. Create a separate property when needed. Inspect its current agent, knowledge sources, theme, Secure Mode and IP-tracking state before changing them. Do not purchase a plan or add unrelated messaging channels as part of routine setup.

## Curated product knowledge

Read the actual public routes and owning source. Cover what the product does, account requirements, primary setup/action, language changes, result/history access, supported limits, technical troubleshooting, support contact and data requests. Keep uncertain or pending behavior explicit. A title guide is not proof of playback support, and an absent record is not proof of safety or availability.

Keep one tracked product knowledge source beside the app and update Tawk’s enabled Text source or FAQs from it. Public website ingestion can supplement it. Exclude account pages and private records from ingestion. Confirm that the source is saved and enabled, then navigate away and back to verify persistence.

Give the agent a product-specific name and instructions. Ask it to answer in the visitor’s language, give the next action and a verified link, and admit when the supplied information does not answer the question. It must not invent prices, release dates, coverage or a ticket/account action. Signed account context does not grant the agent authority to expose private account details. Keep a product-support assistant distinct from the app’s clinical, legal or other domain assistant.

Check representative actual answers: a new visitor’s setup question, returning user question, an unsupported request, troubleshooting, missing data and every changed locale. Open generated links and verify their destinations. Watch for punctuation attached to raw URLs. Correct the owning knowledge/instructions when the answer is wrong, rather than repeating tests until a desirable answer appears.

## Theme and behavior

Take header, message, text and launcher colours from the site’s real tokens. Set these through Tawk’s supported admin appearance controls. Choose foreground colours with enough contrast. Reuse the product name/logo and locale. Do not reach into the cross-origin iframe with page CSS or invent a customStyle colour API.

Check desktop and narrow mobile layouts, expanded/minimized chat, close/minimize controls, keyboard focus and overlap with the main action. Default to an icon-only launcher with the attention grabber off. Disable the automatic welcome/site-notification trigger, desktop and mobile message previews, sound and browser-tab notifications. Set Default View to Chat so opening the widget goes straight to the conversation without a generic welcome screen or an unsupported reply-time claim. Keep greetings inside the chat after the visitor opens it; preserve unread replies from a conversation the visitor started. Verify these settings in every property and locale, then reload the live site to check the minimized footprint. Disable unsent typing previews and file upload where the support task should not collect drafts or sensitive records. Keep required privacy/consent controls intact.

When automating admin forms, verify the rendered value and persisted value after saving. Some text controls update their view before their model; a successful click alone is not proof that the intended setting was saved.

Keep only the requested screenshots and close task-owned tabs/sessions and preview servers after checking. Do not close unrelated user pages.
